# Security

## Reporting

Please report vulnerabilities privately through GitHub's private vulnerability reporting: [Report a vulnerability](https://github.com/danyzmaj-apps/dzep/security/advisories/new) (the repo's **Security** tab). Don't open a public issue. You'll get an answer within a week, and credit in the advisory if you want it.

## Scope

- The apps: Mac (`apps/dzep-macos-app`), iPhone and Android (`apps/dzep-mobile`), and the shared code (`packages/dzep_core`).
- The backend every user deploys: migrations and row-level security, and the `ask`, `device`, `pair` and `push` edge functions (`apps/dzep-macos-app/supabase`).
- The publisher's push relay (`apps/dzep-macos-app/supabase/functions/relay`).
- The Mac's local API, the omp extensions (`apps/dzep-macos-app/integrations/omp`) and the Claude Code plugin (`apps/dzep-macos-app/integrations/claude`).

Out of scope: Supabase, GitHub, Apple, Google and AI providers themselves; a server whose owner shared their account or allowed someone's sign-up; attacks that need an unlocked device you already control.

Most valuable to hear about: anything that lets one account read or write another's data, reach the terminal bridge, read a push's contents, get past the relay's checks or limits or make it send anything but ciphertext or a checked Live Activity state, or run the AI on someone else's server.

## Model

- **No shared server.** Each user runs their own Supabase project. Every table has row-level security that limits a user to their own rows, and the apps hold only the publishable key.
- **Private sign-up.** GitHub is the only way in: email and password sign-up is off (`[auth.email] enable_signup = false`, and the setup wizard turns the email provider off), and the `before_user_created` hook also refuses email, phone and anonymous sign-ups (except the demo account below, made by the server). After the first account it lets in only the emails listed in `allowed_signups`.
- **Pairing.** A phone signs in by scanning a one-time code from the Mac: 28 random characters, of which the server keeps only the SHA-256; single use, valid 10 minutes. Ten wrong tries from one address in 10 minutes are turned away for a while; the address is `cf-connecting-ip`, which Supabase's Cloudflare edge sets (`x-forwarded-for` and `x-real-ip` are ignored, since a client can write them), so a local stack has no throttle. The code space is what makes guessing hopeless. Redeeming it gives the phone a fresh session of its own. Phones never set up servers and never sign in with GitHub.
- **Reviewer codes.** Made by the owner on the Mac (**Settings → Reviewer access**) for App Store and Google Play review. Unlike phone codes they are reusable until they expire: 7, 30 or 90 days from the Mac (the server accepts 1–365). The server keeps only their SHA-256. Each one signs a phone into a separate demo account on the owner's server, which row-level security keeps away from the owner's data. Ask works for the demo account and runs on the owner's AI key. Once none of its codes works, the demo account is shut out: revoking the last working code (or the owner deleting their account) signs it out everywhere at once, sessions and refresh tokens deleted; a code running out does the same within 10 minutes (pg_cron); and `ask` and `pair` refuse it with 403 from that moment. **Delete account** on the demo account empties it (ideas, chats, device tokens, phones, followed sessions) but keeps the account and the owner's reviewer codes, so codes handed to Apple or Google keep working.
- **AI key.** An edge function secret; it never reaches a client.
- **Device tokens.** The widgets and notification actions authenticate to the `device` function with a random per-device token. The server stores only its SHA-256, and sign-out deletes it.
- **Push encryption.** Each phone makes a 32-byte AES key and gives it only to its own server at registration. The server seals every notification with AES-256-GCM (random 12-byte nonce) and sends `base64(nonce ‖ ciphertext ‖ tag)` to the publisher's relay, which passes it to APNs (iPhone, decrypted by the notification service extension) or FCM (Android, a data-only message decrypted by the app). The relay sees the push token, the kind, a collapse id and ciphertext, and stores nothing. Exception: iPhone Live Activity updates can't be encrypted, so they carry only a coding session's state, a timestamp and, when it needs you, what for (a question, an approval or a plan), never text. The relay's APNs key and Firebase service account are its secrets alone.
- **The relay is open by design.** It can't tell callers apart: self-hosted servers hold no publisher credentials. Anyone who knows a phone's push token can make it show a generic alert (title "Džep", text "Reminder" or "Terminal"), or move or end one of its Live Activities, and nothing more; real text needs the phone's key. Each relay instance limits callers in memory (best effort): 600 requests a minute per caller address (`cf-connecting-ip`), 60 pushes a minute per device token, and a caller with 30 bad requests or unknown tokens in 10 minutes gets 429 for a while.
- **Local API.** The Mac's API listens on 127.0.0.1 only, behind a random token in `~/.config/dzep/cli.json` (mode 600; Džep keeps its own `~/.config/dzep` folder at mode 700, and if that `chmod` fails it writes no token). omp's extensions and the Claude Code plugin use the same token, but only after the server proves it holds it: they ask `/v1/ping` with a fresh nonce, without the token, and expect an HMAC-SHA256 of the port and nonce under the token, so whatever listens on a port a stale `cli.json` names gets neither the token nor any commands. Džep removes the file when it quits. Of the terminals, kitty is reached over its unix sockets in `/tmp`, and only sockets owned by the current user count.
- **Terminal from the phone** lets anyone signed in to the account read the Mac's coding sessions (omp, Claude Code) and terminal screens (kitty, tmux, WezTerm, iTerm2, Terminal, Ghostty), prompt them, answer their questions and approvals, type into the terminal windows, and open or close windows. It is off by default and uses a Realtime channel only that user can join; nothing it carries is stored on the server.
- **Updates.** Mac updates are accepted only when signed with the project's Sparkle EdDSA key, and they arrive notarized. Phone builds come from the App Store and Google Play (Play App Signing).
